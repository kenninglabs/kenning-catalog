# Cross-Repo Tracing — Generic Methodology

**Triggers:** following one user request across multiple services when each service emits its own trace ID and there's no end-to-end trace context propagated between them.

> **Project-independent.** How to follow a single user-action across multiple services when each service emits its own trace ID. Distilled from working flows in distributed Spring Boot + Node.js + multi-DB architectures.

## The core problem

Most distributed tracing frameworks generate **per-service trace IDs**, not a single end-to-end trace. So:
- Service A's `[traceA, spanA]` log line is unrelated to service B's `[traceB, spanB]` log line, even if they're handling the same user request.
- You cannot grep a single trace ID across all services and get the full lifecycle.

You need to **correlate by business fields** — values that propagate end-to-end and appear in logs at every hop.

## The methodology

### Step 1 — Find the entry point in the upstream-most service

Pick a search anchor that's likely to appear in the first service hit. Good anchors:
- Account number / customer ID / external identifier (appears in decrypted core-banking responses)
- Application number / order ID / submission UUID (generated at the user-facing layer)
- Username / teller ID / actor identifier (appears in audit logs of every service)

```bash
# Find the request entry point — replace <ARGOCD_APP> and <SERVICE> with project-specific values
<argocd-or-rest-log-fetch> | grep "<BUSINESS_ANCHOR>"
```

The first match gives you the **entry-point trace ID** (the bracketed `[traceId, spanId]` value at the start of each log line in most Java services).

### Step 2 — Get the full trace within that service

Use the entry-point trace ID to see everything that happened in that service for this request:

```bash
<log-fetch-for-same-service> | grep "<TRACE_ID_FROM_STEP_1>"
```

Within one service, trace ID grouping is reliable. You'll see the full request lifecycle: controller entry → business logic → downstream calls → response.

### Step 3 — Extract correlation fields from step 2's output

Look in the step-2 output for **business fields that get passed downstream**:
- Customer name, PAN/SSN, application number, etc. — appear in decrypted payloads
- Internal IDs that bridge services (e.g., a CIF number generated by the upstream service and consumed by the downstream)

These are your handoff anchors for the next service.

### Step 4 — Search downstream services by correlation field

```bash
<log-fetch-for-downstream-service> | grep "<CUSTOMER_NAME_OR_PAN_OR_APP_NUMBER>"
```

Each match gives you that downstream service's trace ID for the corresponding hop. Use that to drill in (back to step 2 logic, scoped to the new service).

### Step 5 — Correlate by `(actor, timestamp)` window when business fields fail

If the business field is too generic (common name, batch reference shared across requests), narrow with timestamp:

```bash
<log-fetch> | grep "userName: <ACTOR_ID>" | grep "<HH:MM>"
```

Audit-interceptor logs typically capture `userName + timestamp`, which is the most robust cross-service correlation.

## Common correlation fields (typical sources)

| Field | Where it's generated | Where to find it in logs |
|---|---|---|
| Account / Customer ID | Upstream request payload (user input) | First service's controller entry; decrypted-payload log lines |
| Trace ID (per service) | Tracer auto-generated per request | Bracket prefix `[traceId, spanId]` in every log line within that service |
| Application / Order Number | Generated at the maker step | Domain entity; audit-interceptor body |
| Customer Name / PAN | External-system response | Decrypted-response log line |
| Actor / Teller ID | Auth context | `AuditInterceptor` `userName` field |
| Timestamp | Logging framework | Every log line |

## Log format normalization

When tracing across services with different stacks, the log formats often differ. Be explicit about the layout each service uses so a `grep` on the right column works:

| Stack | Typical format |
|---|---|
| Spring Boot (Java) | `YYYY-MM-DD HH:mm:ss LEVEL [traceId,spanId] class - message` |
| Spring Boot with custom format | `DD-MM-YYYY HH:mm:ss [traceId - spanId] thread=X service=Y level=Z logger=class message` |
| Node.js (varies) | Often JSON-per-line with explicit `traceId` field |
| Go (Zap/Logrus) | Often JSON or key=value structured |

Date format especially varies (`YYYY-MM-DD` vs `DD-MM-YYYY` vs ISO-8601). When grepping by timestamp, double-check which format each service uses.

## Gotchas

- **Trace IDs don't span services unless you've explicitly wired up W3C Trace Context propagation.** If you haven't, business-field correlation is your only option.
- **Encrypted payloads** — services that AES/RSA-encrypt request/response bodies (often gateways to core banking) leak no business fields in encrypted log entries. Look for the corresponding `Decrypted with <cipher>` line emitted by the encryption library; that has the searchable plaintext.
- **Multi-pod ingestion** — production runs N pods per service. Log fetchers may interleave; look for monotonic timestamps within each pod's stream and treat the per-pod stream as the unit of grep.
- **Old traces rotated out** — log retention is typically minutes to hours for default `--tail` values. For incidents older than that, pull a wide window (`--tail 100000+`) or grab from your log archive (Loki, ELK, etc.).
- **Async producer/consumer split** — Kafka producers and consumers each generate their own trace ID. The Kafka headers usually carry the producer trace ID; check for `KafkaProducer` / `KafkaListener` log lines and grep for the message key or payload field.
